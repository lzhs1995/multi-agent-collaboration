# Runtime model and acceptance evidence

Use this reference when an existing task specifies a model, account scope or
chapter integration result. Reuse its registered controller and original evidence.
These distinctions add no enrollment, model probe, approval loop or new observer.

## Read the actual model request

A profile's default model, alias, startup arguments and screen label describe
different layers. A long-running original session can keep requesting an older
model after a profile's default changes. Use the original client's request record
and the corresponding gateway request to establish the requested model. Record
the upstream response separately; an accepted model name does not prove useful
output or account entitlement. If the next request has not happened, current
runtime model selection remains unverified.

When the requested change is already authorized, the original session owner can
use the installed client's supported model selector at a safe input boundary.
Preserve drafts, outstanding requests, the original session and route. A normal
resume with an explicit model is another supported option only under the existing
recovery contract. Do not rewrite a shared profile for unrelated sessions, replay
a failed request to obtain evidence, or count a model switch as an account repair.

## Distinguish account restrictions from route guarantees

An account list scoped to one provider can exclude that provider's other accounts
while leaving unnamed providers eligible. Do not describe it as a global allowlist
without evidence from the same running implementation. Bind the caller, model,
provider/account scope and fallback behavior to the original task contract.

Prefer an existing complete request attempt chain to a final usage row. The final
row can attribute one account while preceding attempts failed for other reasons.
Distinguish balance, provider policy, removed groups, cancellation and exhausted
fallback. Keep missing historical requests unknown; do not recreate them by sending
new model traffic. A historical success on a different route does not satisfy a
registered comparison's original route or account requirements.

A binary hash identifies an artifact. A few pinned source files or a passing test
of a later working tree do not prove its complete runtime behavior. Where source
provenance is incomplete, the original implementation owner can prepare a fully
bound future candidate and test normal and fallback paths offline. Any adoption
retains its existing scope and startup conditions. Do not change a provider-local
default globally merely to satisfy one caller's stricter task.

## Accept the contribution at its actual scope

Keep these observations separate:

| Observation | What it establishes |
| --- | --- |
| Original target's native receipt | The specified message reached that conversation. |
| Complete input/body read | The applicable versioned inputs were exposed to that agent. |
| Native production and matching artifact | The original agent produced the scoped result. |
| Supervisor reads and integrates the result | Adoption into the named output and version. |
| Manuscript acceptance | The required manuscript checks and adoption actually occurred. |

A chapter-interface contributor is not automatically a chapter supervisor. A
senior supervisor may accept two wording corrections into a synthesis candidate
while the mother manuscript, chapter teams and formal experiment remain unfinished.
Keep that useful contribution, report its actual scope and continue from it; do
not discard it because the full project is incomplete or count it as a formal run.

Return substantive feedback through the original route when the task calls for it.
Its receipt does not prove the recipient read the feedback. Preserve pending reads
without another ACK loop or a repeated review of unchanged material. The existing
scope's review count, unresolved source gaps and original failed attempts remain.
